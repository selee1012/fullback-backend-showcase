## 2. 개발 중 방향을 바꾼 사례

최종 발표에서 별도 슬라이드로 다룬 **"외국인 경험을 해칠 수 있는 부분"** 4가지입니다. 모두 개발 중기 사용자 리뷰에서 나온 피드백이 계기였습니다.

### ① 카카오맵 → 구글맵 전환

**문제** — 카카오맵은 국내 지리 정보는 정확하지만 다국어 라벨 지원이 제한적입니다. 외국인 사용자가 지도를 봐도 한글 지명만 보이는 상황이 발생했습니다.

**결정** — 주 지도를 구글맵으로 전환. 다만 한국 내 상세 정보는 카카오맵이 나은 영역이 있어, **카카오맵은 딥링크 대상으로 유지**하고 두 지도 서비스 링크를 모두 제공하는 구조로 정리했습니다(`Place.link_url_google`, `Place.link_url_kakao`).

### ② UI 한글 잔존 → 다국어 전수 점검

**문제** — 주요 화면은 번역했지만 에러 메시지, 버튼 라벨, 상태 텍스트 등에 한글이 남아 있었습니다. 타겟 사용자가 외국인인 서비스에서 한 곳이라도 한글이 보이면 신뢰가 깨집니다.

**결정** — 전 화면 전수 점검. 백엔드에서도 응답 데이터(`name`, `level`, `tag`, `description`, `startAccess`/`endAccess`)를 모두 언어별 컬럼으로 분리해 **서버가 한국어를 내려보낼 경로 자체를 없앴습니다.**

### ③ 주변 관광지 데이터 부족 → 크롤링 및 데이터 보강

**문제** — 공공데이터만으로는 코스 주변 POI가 빈약해, "산책로 + 주변 인프라 통합"이라는 핵심 가치가 성립하지 않았습니다.

**결정** — 크롤링으로 외국인 선호도가 높은 맛집·관광지를 보강하고, `PlaceRecommend` 매개 테이블로 코스별 큐레이션을 구성했습니다. 최종적으로 정제된 POI 100건 이상을 확보했습니다.

### ④ 커뮤니티 신뢰도 → 다국어 금칙어 LLM 필터

**문제** — 비인증 환경에서 누구나 쪽지·리뷰를 남길 수 있어 악용 여지가 있었습니다.

**결정** — Solar LLM 기반 모더레이션 + Rule-Based 폴백의 2단 방어 도입 → [06. LLM 비속어 필터링](06-llm-moderation.md)

### ⑤ (추가) 반경 3km에 코스가 없을 때

**문제** — 서울 외곽이나 코스 밀도가 낮은 지역에서 반경 3km 조회 결과가 비어, 사용자가 빈 지도를 마주하는 케이스가 발생했습니다.

**결정** — 반경 내 결과가 없으면 **지도 축척을 전역으로 동적 확장(Zoom-out)** 하여 전체 코스를 재추천하는 예외 처리를 추가했습니다. 빈 화면 대신 항상 무언가를 보여준다는 원칙입니다.

## 3. 백엔드 관점에서 잘한 점

**① 실패를 전제로 외부 연동을 설계했다**

Google Maps도, Solar LLM도 모두 타임아웃·폴백·기능 토글을 갖췄습니다. 특히 LLM 모더레이션은 fail-open으로 설계해, 외부 API가 죽어도 커뮤니티 기능이 멈추지 않습니다. 외부 의존성이 서비스 가용성의 상한이 되지 않도록 한 점이 이 프로젝트에서 가장 만족스러운 부분입니다.

**② 응답 규격과 예외 처리를 초반에 통일했다**

`ApiResponse<T>` + `ErrorCode` + `GlobalExceptionHandler` 조합을 도메인 구현 전에 잡아둔 덕분에, 6개 도메인이 병렬로 개발되는 동안에도 응답 형태가 흔들리지 않았습니다. 프론트엔드와의 연동 비용도 크게 줄었습니다.

**③ 성능 문제를 추측이 아니라 구조로 해결했다**

공간 연산 DB 위임, `@EntityGraph` fetch join, `readOnly` 기본값, `open-in-view: false`는 모두 "느려지면 고친다"가 아니라 **처음부터 병목이 생길 지점을 막는** 선택이었습니다. 결과적으로 부하 테스트에서 별도 튜닝 없이 목표치를 크게 상회했습니다.

**④ 알면서 남긴 부채를 문서화했다**

native query에서 `@EntityGraph`가 안 먹는 문제, 좋아요 토글의 race condition, 애플리케이션 레벨 태그 필터 — 모두 **한계를 인지하고 있으며 해결 방향이 무엇인지**를 코드 주석과 문서에 함께 남겼습니다. 모르고 넘어간 것과 알고 남긴 것은 다릅니다.

## 4. 아쉬운 점과 배운 것

| 아쉬운 점 | 배운 것 |
| --- | --- |
| **DB 제약을 애플리케이션 로직으로 대체했다** | `(course_id, guest_id)` unique 제약을 걸었다면 좋아요 race condition을 코드 없이 막을 수 있었습니다. 동시성 문제는 애플리케이션 체크보다 DB 제약이 확실하다는 것을 배웠습니다. |
| **native query 도입 시 트레이드오프를 늦게 인지했다** | `ST_Distance_Sphere`를 쓰려고 native query를 택했는데, 그 순간 `@EntityGraph`를 잃는다는 것을 나중에 알았습니다. 기술 선택의 **부수 효과**까지 미리 확인해야 합니다. |
| **위치 검증을 시연 편의로 껐다** | 주석으로 보존해 복구는 쉽게 해뒀지만, 기능 토글(설정값)로 만들었다면 더 깔끔했을 것입니다. 임시 비활성은 코드 주석이 아니라 설정으로 다뤄야 합니다. |
| **쓰기 경로 부하 테스트가 없었다** | 조회는 검증됐지만 동시 쓰기 경합은 미검증 상태로 남았습니다. 성능 검증 범위를 정할 때 "측정하지 않은 것"을 명시하는 게 중요합니다. |
| **8주 일정에서 MVP 범위 조정** | 전국 확장은 처음부터 향후 과제로 분리했습니다. 완성도 있는 축소 범위가, 미완성인 넓은 범위보다 낫다는 것을 체감했습니다. |
